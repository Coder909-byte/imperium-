# 006. Puppet clips: sparse authored keyframes, evaluated by a pure function, not per-instance GSAP timelines

## Context

PRD §3/§10 (M6) asks for cutout puppet rigs — parts rotated with GSAP — with a rig library the human will hand-author in M8, with no animation tool. Two decisions were bundled together going in, and needed separating:

1. **Authoring format.** Raw per-frame rotation samples are trivial to play back (index into an array) but brutal to hand-author: producing a smooth walk cycle by hand means computing every in-between value yourself. Sparse keyframes (a handful of `{t, rot, ease}` entries per part per clip) are what every other timed thing in this codebase already uses (`Beat.camera`, `sweepTween.ts`) and let an author write only the meaningful poses.
2. **Playback mechanism.** "GSAP-eased keyframes" doesn't by itself say whether playback is a live GSAP `Timeline`/`Tween` object per instance, or eased values computed by a plain function. Camera.ts already drew this line once, for a different effect: handheld drift runs every frame for the life of a scene, so it's hand-rolled noise, not a GSAP tween — GSAP is reserved for one-off, per-beat moves. Puppet clip playback is the same shape of problem at higher multiplicity: up to 40 individually-phased `PuppetActor` instances (PRD's own M6 acceptance criterion), each with ~12 parts, evaluated every tick.

## Decision

Clips are authored as sparse keyframes (`content/schema.ts`'s `RigClip`/`RigKeyframe` — `t` normalized 0..1, `rot` a delta in degrees from the part's rest rotation, `ease` a GSAP core ease name). Playback (`engine/scene/puppet/clipPlayer.ts`) is a pure function, `evaluateClipRotations(rig, clip, elapsedMs, out)`, that finds the two keyframes surrounding the current time and interpolates between them using `gsap.parseEase(name)` — GSAP's ease *math*, resolved once per keyframe at rig-load time (`rigLoader.ts`), never re-parsed per frame — with no `gsap.to()`/`Timeline` ever constructed for playback. `PuppetActor.tick()` calls this once per frame per instance, writing into a pre-allocated `Float32Array`, then `jointSolver.computeWorldTransforms()` (also pure, also writing into a pre-allocated buffer) composes world transforms down the rig's parent chain and the result is written directly onto already-constructed Pixi `Sprite`s — construct-once-mutate, the same discipline M5's `ParticleField`/`PostChain` already established, with zero per-frame allocation.

## Consequences

Hand-authoring a clip in M8 means writing a few keyframes per moving part, not computing an animation curve by hand — `content/rigs/legionary.json`'s six clips (idle/march/brace/thrust/fall/raise) are 2-5 keyframes per tracked part. Playback stays cheap at the scale M6's own acceptance criterion demands (40 staggered `PuppetActor`s + a 500-unit `CrowdField`, measured — not assumed — at ~16.7ms median frame time unthrottled; see CLAUDE.md's M6 entry) because nothing per-instance owns a GSAP object with its own internal bookkeeping; the cost is a small hand-rolled interpolation loop instead of delegating that loop to a library, the same trade-off `noise.ts` and `sweepTween.ts` already made for their own effects. A second, unplanned benefit: because pose evaluation is a pure function of `(clip, time)`, `/dev/scene-lab`'s rig inspector can scrub to an arbitrary time via the exact same function (`PuppetActor.seek()`) with no separate "scrub mode" — a live `Timeline`-based design would have needed its own `.seek()`/`.progress()` plumbing to support that.
