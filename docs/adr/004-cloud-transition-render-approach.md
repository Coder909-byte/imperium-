# 004. Cloud transition render approach: CSS/SVG, not WebGL

## Context

PRD §8.2 specified WebGL quads with a scrolling noise-displaced alpha mask for the atlas↔scene cloud sweep — reasonable on its face, since it runs on every navigation and is the most-seen animation in the product, and WebGL is what the scene player (M4) will use regardless. But this transition sits between an SVG page (the atlas) and a Pixi page (the scene, from M4 on), covering the swap between them. Spinning up a WebGL context purely for a ~2-second overlay has a cost that doesn't exist for CSS/SVG: context creation, shader compilation, and texture upload sitting directly in front of the single most latency-sensitive interaction in the product, with no idle-prefetch grace period available the way M2's border-morph had (a user can click a province the instant the atlas is interactive). CLAUDE.md's hard rule is "Atlas is SVG. Scenes are Pixi. Do not mix" — a third pipeline for the transition between them is a real cost, not a neutral choice, and the atlas already ships the exact technique this needed: `AtlasFilters.tsx`'s `inkEdges` filter is `feTurbulence` + `feDisplacementMap` distorting a vector edge into a hand-inked wobble.

## Decision

Built with CSS/SVG: two cloud "masses," each a translated `<div>` with three overlapping child blobs and a static `feTurbulence`+`feDisplacementMap` filter (`engine/transition/CloudSweep.tsx`, filter defined once, applied to the mass container rather than each child — see the perf note below), plus 14 parallax puff sprites using a plain radial-gradient circle with no filter. All motion — the sweep, the parallax field, the reduced-motion crossfade — is driven by writing `transform`/`opacity` directly to element refs from a hand-rolled `requestAnimationFrame` tween (`sweepTween.ts`), never through React state per frame and never through GSAP: this component has to be ready on the very first click, so it stays dependency-free rather than risk a lazy-loaded library not being warm yet (unlike M2's MorphSVGPlugin, deferring GSAP here isn't safe — there's no equivalent to "the user has to notice the inset switcher first"). The only new dependency is Zustand (`transitionStore.ts`, ~636B gzip), for the one thing CSS/SVG doesn't solve on its own: triggering the sweep from deep inside whichever page is currently mounted, and having it reach the overlay that lives once in the root layout to survive the actual page swap.

Two claims this decision rests on were verified against a real Chrome trace rather than assumed:

- **MorphSVG-style "static filter, motion on compositor-only properties" holds for the real component.** A real Chrome trace (`Tracing.start`/`Tracing.end` over CDP, not DevTools' UI, but the same underlying data) with per-node attribution shows each of the two mass containers and all 14 puffs paint **exactly once** — when they first appear — and never again for the rest of the animation; every subsequent frame is compositor-only `Commit`/`DrawFrame` work. This ruled out an earlier hypothesis (that per-element filter cost was the bottleneck) once the filter was temporarily stripped entirely and the Paint count barely changed — the real cause of a lower-than-expected fps reading turned out to be unrelated to CloudSweep (see below).
- **A confound was found and separated out, not papered over.** Mouse clicks unavoidably hover before they land, and hovering an atlas province was already triggering a full-`#document` repaint via the pre-existing (M1/M2) `.hovered` `fill-opacity`/`stroke-opacity` CSS transition inside `AtlasFilters.tsx`'s `inkEdges`-filtered `<g>` — confirmed via the same per-node trace attribution, independent of any cloud sweep at all. That repaint, not the clouds, was responsible for most of the gap between measured and target fps in a realistic mouse-click scenario. It's a real, pre-existing characteristic worth a look, but it's atlas CSS, not cloud-transition code, so it's out of this milestone's scope — flagged for a separate look, not fixed here.

Isolated from that confound (synthetic click, no hover), real measured performance: **~55fps at 1× CPU, ~48fps at 4× throttle, ~43fps at 6× throttle**, median inter-frame gap ≈17ms (≈58.5fps) even at 6×, with occasional slower frames (up to ~52ms) rather than a sustained drop — consistent with the one-time element-reveal paint burst plus per-frame JS cost of writing 16 elements' styles becoming non-trivial under heavy throttling, not a structural failure of the technique.

## Consequences

Equivalent visual quality (real procedural noise, real parallax) at a fraction of the WebGL approach's engineering and latency cost, and the atlas route's initial JS grew by only ~2KB gzip (135.9KB vs. M2's 133.9KB baseline, measured via `next start` + `curl`, `noModule` excluded — see CLAUDE.md) — cheap enough to ship eager rather than lazy, which is the actual point: ready on the first click, no context-creation latency, no risk of a cold dynamic import racing a click.

The CPU-throttled numbers above are real measurements but a partial signal, not proof: they're desktop Chromium under `Emulation.setCPUThrottlingRate`, which slows the CPU/main-thread only. They say nothing about mobile GPU compositing throughput or Safari's handling of referenced SVG filters (`filter: url(#id)`), which is historically less compositor-friendly than Chromium's — genuinely untested here, no real device or Safari access in this environment. That remains an open item, not a closed one, for whoever does real-device QA. The pre-existing atlas hover-repaint characteristic uncovered during this investigation is a second open item, filed against M1/M2's `inkEdges`/`.hovered` CSS rather than fixed here.

PRD §8.2 updated to match (CSS/SVG, not WebGL quads).
